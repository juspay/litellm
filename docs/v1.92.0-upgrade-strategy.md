# LiteLLM v1.92.0 Upgrade Strategy

**Date:** 2026-07-15  
**Target:** Juspay `release/v1.83.3` -> upstream `v1.92.0`  
**Planning branch:** `v1.92.0-upgrade-plan-from-v1.83.3-stable`  
**Execution branch:** create a fresh branch from `release/v1.83.3` after this plan is reviewed.

## TL;DR

Keep this branch documentation-only. Use it as the audit and replay reference.

For the actual upgrade, create a fresh branch from `release/v1.83.3`, reset the working base to upstream `v1.92.0`, then replay Juspay custom commits in domain batches. Reuse the conservative process from the `v1.83.3` upgrade: every custom behavior is either carried forward, reworked onto the new upstream surface, or dropped only when upstream behavior is proven equivalent.

The local repository was shallow when this plan started. After unshallowing, the current inventory is:

- **142 non-merge commits** in `v1.83.3-stable..release/v1.83.3`.
- This includes runtime customizations, post-`v1.83.3` fixes, service-account work, MPR zset work, and old `.upgrade` planning artifacts.
- Upstream `v1.83.3-stable..v1.92.0` contains **3588 commits**.
- `v1.92.0` is a plain stable tag; LiteLLM no longer uses `-stable` suffixes for new stable releases.

## Recommendation

Yes, the proposed branch strategy is sound:

1. Use `v1.92.0-upgrade-plan-from-v1.83.3-stable` for plan artifacts only.
2. Review and refine the batch/audit strategy here with team input.
3. Create the real upgrade branch from `release/v1.83.3`.
4. Reset that branch to upstream `v1.92.0`.
5. Replay only the audited custom commits.
6. Use this plan branch as the reference for batches, drop-gates, dry-runs, and verification.

## Goals

- Land on upstream `v1.92.0`.
- Preserve all Juspay runtime behavior that is still needed.
- Avoid carrying old upgrade-planning artifacts into the new runtime branch unless deliberately archived.
- Avoid opportunistic refactors during replay; rework only where upstream surfaces changed.
- Verify the high-risk behavior with concrete evidence before merge.

## Non-Goals

- Do not add new product features during the upgrade.
- Do not rewrite old custom systems just because upstream added adjacent functionality.
- Do not drop a customization because it "looks covered" by upstream.
- Do not use this planning branch for the actual code replay.

## Inventory Method

Before audit, regenerate the current replay inventory:

```bash
git fetch upstream --tags
git fetch origin

git log --reverse --no-merges --format="%H|%ad|%s" --date=short \
  v1.83.3-stable..release/v1.83.3 \
  > .upgrade/v1.92.0/replay-matrix.csv
```

Then split the matrix into:

- **Runtime commits:** custom behavior we may need to carry.
- **Upgrade artifacts:** old `.upgrade` docs, old replay notes, old verification reports. Default decision should be `DROP` from the runtime replay, or archive under docs if the team wants to preserve history.
- **Backports already upstream:** commits ported from later upstream versions. Default decision is `DROP` if `v1.92.0` contains the same patch with equivalent semantics.

## Audit Decision Tree

For each commit:

1. Identify the actual behavior, not only the files touched.
2. Check upstream changes in the same files/functions:

```bash
git show <sha> --stat
git show <sha>
git log --oneline v1.83.3-stable..v1.92.0 -- $(git show --name-only --format= <sha>)
git diff v1.83.3-stable v1.92.0 -- $(git show --name-only --format= <sha>)
```

3. Decide:

| Decision | Meaning |
|---|---|
| KEEP-AS-IS | Upstream did not touch the surface, or the cherry-pick applies cleanly with identical behavior. |
| REWORK | Our behavior is still needed, but upstream changed the surrounding code. |
| DROP | Upstream fully covers the same behavior with equivalent semantics. |
| CONDITIONAL DROP | The patch becomes a no-op after earlier rework; verify during replay. |

## Drop Gate

All four conditions must be true before dropping a runtime custom patch:

1. Upstream equivalent is cited by SHA/PR or a precise diff.
2. Semantics match: same env vars, headers, Redis keys, DB fields, response shape, metrics, and access-control behavior.
3. A verification item exists in `.upgrade/v1.92.0/verification/MUST-SURVIVE-VERIFICATION.md`.
4. A human reviewer signs off in the audit row.

If any condition is false, default to `KEEP-AS-IS` or `REWORK`.

## Proposed Execution Flow

### Phase 0: Safety

```bash
git checkout release/v1.83.3
git pull --ff-only origin release/v1.83.3
git branch backup/pre-v1.92.0-upgrade-$(date +%Y%m%d) release/v1.83.3
git push origin backup/pre-v1.92.0-upgrade-$(date +%Y%m%d)
```

### Phase 1: Audit

- Regenerate `replay-matrix.csv`.
- Split commits into the batches above.
- Fill one audit file per batch.
- Start with batches 05, 07, 04, 06 because these have correctness and security blast radius.

### Phase 2: Dry Run

Create a scratch branch from `v1.92.0` and sample the riskiest commits:

- latest MPR zset commit `325975bff5`
- service-account automation `fa38ff2b42`
- service-account schema/user/key changes `28b1e4c604`
- GCS/logprobs pair `73479de8d0` and `05e41940be`
- budget and FREE_MODELS commits from the prior upgrade
- sticky least-busy Redis commits
- read replica / Prisma self-heal fixes

Record marker counts and conflict files under `.upgrade/v1.92.0/dry-run-findings.md`.

### Phase 3: Replay

```bash
git checkout -b upgrade/v1.92.0-from-release-v1.83.3 release/v1.83.3
git reset --hard v1.92.0

while read sha; do
  git cherry-pick -x "$sha" || { echo "CONFLICT on $sha"; break; }
done < .upgrade/v1.92.0/batches/<batch-file>
```

Rules:

- Use `git cherry-pick -x`.
- Replay one batch at a time.
- Tag each green checkpoint.
- If a `KEEP-AS-IS` commit conflicts, stop and re-audit.
- Do not replay old `.upgrade` artifacts unless we explicitly choose to archive them.

### Phase 4: Verification

Run the MUST-SURVIVE checklist with evidence. Attach logs, screenshots, command outputs, and dashboard links.

### Phase 5: Ship

- PR from upgrade branch to `release/v1.83.3` or the agreed release target.
- PR description links this plan, audit docs, dry-run findings, and verification evidence.
- Burn in sandbox first, then canary, then promote.

## Early Opinion

The actual replay will be heavier than the previous jump in **surface complexity**, not necessarily commit count. The most dangerous areas are:

- MPR zset limiter versus upstream rate-limit changes.
- Service-account flow versus upstream RBAC/security hardening.
- GCS/logprobs in hot request/logging paths.
- Existing budget/fallback/routing behavior versus upstream routing and Responses API changes.

The plan should therefore optimize for semantic audit and dry-run evidence, not just low conflict counts.
